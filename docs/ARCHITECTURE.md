# Wenyan 结构与数据边界

这不是传统“架构设计文档”。它只固定那些**以后改代码时最容易误伤、但又必须保持清楚的边界**。

## 1. 当前技术形态

Wenyan 当前是轻量静态 Web 应用：

- HTML + CSS + Vanilla JavaScript
- Vite 仅用于开发和构建
- `ts-fsrs` 用于复习调度
- 没有业务 Node 后端
- 没有账号系统
- 没有数据库作为运行前提
- 学习状态本地优先保存

除非现有方式已经明显妨碍真实使用，否则不要因为“更现代”重写框架。

## 2. 代码地图

### 界面与交互

- `src/app.js`：页面渲染、路由、训练交互、设置面板、搜索等。
- `src/style.css`：当前选定视觉与响应式行为。
- `index.html`：应用入口。

### 内容

- `src/content.js`：文学小样、练习、小量兼容种子词。
- `src/english-vocab.js`：考研英语词库加载、缓存、降级与旧记录兼容层。

内容数据应当可审核、可追溯；不要把用户个人学习状态混进内容文件。

### 学习状态

- `src/core.js`：事件合法性、合并、FSRS 排程、拼写规范等纯逻辑。
- `src/storage.js`：localStorage 保存与多标签合并。
- `src/backup.js`：学习记录导入导出。

这三处属于高风险区。修改前先理解现有 schema 和兼容逻辑，修改后必须跑测试。

### 测试与旧版

- `tests/`：保护学习数据、排程、备份、设备宽度等关键行为。
- `legacy/`：旧版资料与旧入口，当前阶段默认保留，不以“清理”为理由删除。
- `evidence/`：验收截图，不包含真实个人学习内容。

## 3. 必须保持稳定的数据边界

### 学习事件

主要记录键：`wenyan-events-v2`。

原则：
- 已有事件 ID 不重写。
- 合并优先去重，不覆盖另一设备/标签已完成的记录。
- 无法读取时不静默清空。
- 任何 schema 变化都必须先设计向后兼容或迁移方案。

### 英语单词 ID

稳定 ID 使用规范化英文单词本身，并继续写成 `word:<id>` 形式进入学习记录。

因此：
- 换词库不能随意换 ID。
- 已有收藏、已掌握、复习记录和未完成 session 必须继续找到对应单词。
- 外部词库只是内容来源，不拥有学习状态。

### 阅读位置与未完成训练

阅读位置、英语 session、文学回忆 session 都属于“续学体验”。任何重构都要检查：
- 刷新后能否继续。
- 关闭页面后能否继续。
- 导出再导入后能否继续。

## 4. 内容与来源边界

正式学习内容必须区分：

1. **事实源 / 原始证据**：官方信息、教材、原典、真题、论文等。
2. **Wenyan 自编整理**：摘要、提纲、题目映射、复习提示。
3. **第三方数据**：如英语词频数据，必须保留许可和署名。

AI 只能帮助整理和表达，不能把自己当作知识来源。

## 5. 页面结构边界

一级入口保持：
- 今日
- 知识
- 训练

新功能优先挂在这三个入口下，不轻易增加一级导航。

设计基准继续参考 `docs/design/selected-reference.png`。除非真实使用证明现方向有问题，否则不要重新做一套视觉系统。

## 6. 云同步未来怎么接

云同步是薄层，而不是重新设计整个状态系统。

预期方向：
- 学习动作先落本地。
- 云端交换事件列表或等价的可合并状态。
- 稳定 ID 去重。
- 失败不阻塞本地学习。
- 用户始终保留手动备份能力。

不要先建完整用户中心、权限系统或复杂同步协议，再寻找使用场景。

## 7. 什么时候才值得拆文件或升级架构

满足至少一个条件再做：
- 单个文件已经明显难以安全修改。
- 同一模块存在多个独立生命周期。
- 测试或复用确实被当前结构阻碍。
- 真机性能数据证明当前实现不够。

“看起来更规范”本身不是拆分理由。
